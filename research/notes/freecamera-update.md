## 1. 结论

当前 FreeCamera 的状态更新源已经收敛到 **SpectatorCameraController 的共同基类更新路径**，不能把当前实例称作 CinemaCameraController。两者共享非虚更新函数和数据布局，但在配置分支及约束处理上存在差异。

只恢复 FreeCamera 的位置、方向和 FOV 不足以获得稳定机位：原生控制器另存目标位置、目标/平滑角度、计算出的方向和 up、FOV 动画状态，更新会继续把这些值施加到相机。读取成功与恢复成功仍是两个验收阶段。

这次找到了具体更新代码、原生 setter 和矩阵缓存链，也得到了主代理当前运行的对象关联结果。**没有实际进行写回，因此没有证明恢复成功、原子提交、无抖动或不会发生其他覆盖。**

## 2. 对象身份与当前分支

### 2.1 FreeCamera 的创建者

RTTI 直接给出的主 vtable：

| 类型 | preferred vtable VA |
| --- | --- |
| `DAVA::Camera` | `0x0369C83C` |
| `FreeCamera` | `0x0372040C` |
| `GameSceneController` | `0x037203B4` |
| `BaseSpectatorCameraController` | `0x0370DDFC` |
| `CinemaCameraController` | `0x0370E094` |
| `SpectatorCameraController` | `0x0370FAB0` |

`0x0171B620` 分配 `0x26C` 字节，调用 FlexFOV 基类构造，`0x0171B68D` 写入 FreeCamera vtable；`0x0171B6D2` 将该对象保存到 `GameSceneController + 0x94`。后续创建实体并存入 `+0x98`。

`GameSceneController` 的次 vtable 分别位于 `0x037203C8(+8)`、`0x037203D8(+0xC)`、`0x037203E8(+0x10)`、`0x037203F4(+0x14)`、`0x03720400(+0x18)`。这些是同一对象的子接口，不应当作六个独立控制器。

构造函数 `0x01710BF0` 中：

```text
01710C75  mov ecx,[eax]       ; 第一个参数包装中保存的对象
01710C77  mov [edi+1Ch],ecx
01710C7E  call 0091D6C0       ; 非空时 retain
01710C87  mov eax,[ebp+10h]   ; 第三个参数包装
01710C91  mov ecx,[eax]
01710C93  mov [edi+20h],ecx
01710C9A  call 0091D6C0       ; 非空时 retain
```

这证明 `+0x20` 是构造时保存并持有引用的正向对象槽。仅凭这些指令不能命名它的具体动态类型；本轮主代理额外核验该槽指向 `AvatarContextReplay`，因此可以将它纳入回放身份检查。

### 2.2 Cinema 与 Spectator 的条件创建

`0x01595C40` 从配置对象读取 `+0x52D` 字节，分配同样大小 `0x138` 的控制器并保存到所属对象 `+0x68`：

```text
配置字节为真：0x01595CDA → 0x015CE640 → Cinema vtable 0x0370E094
配置字节为假：0x01595D29 → 0x01616D90 → Spectator vtable 0x0370FAB0
两种构造均调用 0x015CD6B0（BaseSpectator 基类构造）
```

本轮未独立追完 `+0x52D` 配置字段与 YAML 名称之间的生成绑定，不把这个偏移仅凭位置硬命名为 `Dev Cinema Camera`。确定的是这条当前 EXE 中存在的二选一创建分支。

共同更新调用边：`0x015B85AC` 读取所属对象 `+0x68`，`0x015B85AF` 调用非虚函数 `0x01607570`。另一模式分支使用所属对象 `+0x2C`，通过 `0x01607550` 调用另一对象 vtable `+0x20`，不能混用。

两种派生控制器的 virtual slot 6 有真实区别：Cinema 指向 `0x006B6E70`，直接返回 false；Spectator 指向 `0x0161E460`，可按场景条件调用 `0x0074F830`。共同更新会依据此返回结果选择候选位置/约束分支。后者详细碰撞算法未完全命名，不能声称已关闭所有碰撞或地图边界。

## 3. 每次更新会怎样覆盖状态

下表字段均相对于 `BaseSpectator/Spectator/Cinema` 控制器，不是相对于 FreeCamera。

| 字段 | 当前指令证明的用途 | 对恢复的影响 |
| --- | --- | --- |
| `+0x0C` | 被控制 Camera 指针 | 必须等于当前场景/渲染引用的 FreeCamera |
| `+0x10..+0x2D` | 输入状态字节组，不同分支读取不同字节 | 持续按键或残留事件仍可推进目标；不能无差别改整个结构 |
| `+0x58/+0x5C` | 两个目标角度；输入增量累加于此 | 只写相机方向会被旧目标方向覆盖 |
| `+0x60/+0x64` | 两个平滑中的当前角度 | 恢复目标角度而不恢复当前角度仍可能缓慢过渡 |
| `+0x80/+0x84` | 本次角度输入增量，更新末尾清零 | 保存应在松开输入且停稳后进行 |
| `+0x88` | FOV 输入增量，处理后清零 | 恢复时应无待消费的 FOV 输入 |
| `+0x9C/+0xA0/+0xA4` | 三个平移输入分量，消费后清零 | 不能仅恢复 camera position |
| `+0xAC/+0xB0/+0xB4` | 目标位置 | 下一次位置平滑仍向此处移动 |
| `+0xB8/+0xBC/+0xC0` | 由平滑角度产生的方向向量 | 更新会用它重设 camera target，长度未必为 1 |
| `+0xC4/+0xC8/+0xCC` | 计算后的 up 向量 | 每次更新会重新施加到 Camera |
| `+0xFC` | 位置平滑系数 | 本轮实读约 3.2222；不是可直接宣称的飞行米/秒 |
| `+0x110` | 绕视线产生 up 的角量，直接用于 sin/cos | 与 Camera 自己以度表示的 roll 是两套不同状态 |
| `+0x114/+0x118` | 当前/目标接口 FOV | 更新会持续同步 `+0x114` 到 Camera；滚轮目标还可驱动动画 |
| `+0x134` | 动画相关对象 | 未验证是否存在待完成动画，不可复制其指针来“恢复” |
| `+0x10C/+0x128` | 跟踪/模式分支条件；自由分支为 `-1/0` | 第一版应拒绝未验证的其他分支 |

### 3.1 位置平滑已是直接代码证据

`0x016076FE..0x01607790` 取当前相机位置，与 `controller+0xAC` 目标位置作差，然后乘入传入的 dt 和 `controller+0xFC`，再加回当前位置：

```text
p_candidate = p_camera + (p_goal - p_camera) * dt * smoothing
```

随后 `0x016077CB` 调用 virtual slot 6，经过约束分支，`0x01607823` 或 `0x0160789C` 调用位置 setter。这里证明存在“向目标追赶”的算法；dt 的实际时钟来源、更新频率及所有约束是否生效仍需结合上层/运行时记录，不能仅据此断言精确惯性时长。

`0x01608250` 消费平移输入，用当前相机方向、另一个相机基向量及竖直分量构造位移，乘 dt 后推进 `+0xAC`，并对空间范围进行检查/钳制。它解释了目标状态为何可以在相机停止接收新的按键后仍与相机当前值不同。

### 3.2 角度与 up

`0x01608F90` 将输入增量累加到目标角度，对俯仰作范围处理；`0x01609040..0x01609082` 用 `current += (target-current)*dt*coefficient` 更新 `+0x60/+0x64`，最后于 `0x016093D3..0x016093EA` 写入方向 `+0xB8..+0xC0`。

`0x0160BA10` 从 `+0x110` 计算 sin/cos，结合方向向量和默认世界 up 生成 `+0xC4..+0xCC`。更新在 `0x016077B3` 调用相机 up setter，`0x016078BD` 调用相机 direction setter。因此普通 FreeCamera 的 up 也不是独立永久的权威输入。

相机自身 `+0x5C` 的 roll 在矩阵阶段另乘 PI/180。未来组合姿态时不能同时把同一个滚转全部编码进 up 和 Camera roll，否则可能重复施加；保存/恢复阶段先保留原生两套状态各自的精确值，不自行转换。

### 3.3 FOV

更新 `0x01607926..0x01607A2B` 将 FOV 输入作用于 `+0x118`，经过动画相关调用影响 `+0x114`，再把 `+0x114` 通过相机 vtable `+0x10` setter 施加到相机。构造调用 `0x016079DA → 0x0125CB20` 传入浮点 `0.5`，但本文未完整确认其参数类型/时间单位，不把它写成已验证的动画时长。

FreeCamera 的 FOV setter `0x01503060` 保存接口 FOV 到 `camera+0x268`，乘 `camera+0x264` 的缩放，钳制在 1..140 后调用 Camera 基类 setter `0x00E78990`。基类写 `+0x2C` 并更新投影参数。因此必须同时区分控制器 FOV、接口 FOV 和实际投影 FOV；不能只写 `+0x2C` 然后期望原生更新保持它。

## 4. Camera setter 与 dirty 链

以下语义名称由当前指令行为归纳，不是公开导出的 API 名称：

| preferred VA | 直接行为 |
| --- | --- |
| `0x00E7B0B0` | 复制位置到 `+0x38`；可能同步关联对象；`flags(+0x248) |= 0x1` |
| `0x00E7B6E0` | 复制 target 到 `+0x44`；可能同步关联对象；`flags |= 0x1` |
| `0x00E78490` | `target = position + direction`，写 `+0x44`；`flags |= 0x1` |
| `0x00E7B440` | 保存 roll 到 `+0x5C`；`flags |= 0x1` |
| `0x00E7BA80` | `+0xC` 关联对象为空时直接保存 up 到 `+0x60`，否则向关联对象传递；`flags |= 0x1` |
| `0x00E53C80` | 从 `target-position` 重新计算并归一化 `+0x50`，返回该缓存 |
| `0x00E78990` | 基类 FOV setter；关联对象为空时写 `+0x2C`，调用 `0x00E6DB50` |
| `0x00E77CA0` | aspect setter；关联对象为空时写 `+0x28`，调用 `0x00E6DB50` |

`+0x50` 是可被 getter 重算的缓存，不能作为唯一方向权威字段；单独写它会被下一次 getter 覆盖。

`0x00E5B4A0` 展示明确的缓存失效处理：

```text
mask 0x1 → 0x00E6BAF0：position/target/up → 基视图 +0x80；置 0x2、清 0x1
mask 0x4 → 0x00E6D730：投影范围/近远面/aspect等 → projection +0x100；置 0x8、清 0x4
mask 0x2 → 0x00E6DA70：基视图与 roll（度×PI/180）→ view +0xC0；置 0x8、清 0x2
mask 0x8 → view×projection → VP +0x140；清 0x8
```

`0x00E6DB50` 除置 `0x4` 外还重算投影范围等中间值。因此直接改 FOV 并只置投影 dirty，可能仍使用旧的投影范围；不能把“一个 flags 写入”当作完整 FOV setter 替代。

相机还存在 `+0x8/+0xC` 关联对象路径、其他矩阵/视锥相关缓存。首版恢复实验必须保持当前已观察到的 `+0x8 == +0xC == 0` 前提，或另行研究关联对象同步；不得套用到任意 Camera。也不能只回填 view/VP 就宣称完整相机恢复。

## 5. A 步骤的可执行准备与写回方案边界

### 5.1 现在可做的读取准备

1. 每次开始重新核对 EXE 哈希、重定位后的 RTTI/vtable 与指针链，不复用本次堆地址。
2. 正向检查 `GameSceneController+0x20` 为已验证的 `AvatarContextReplay`；`+0x1C` 为当前 GameScene；`+0x94` 与 Scene/RenderSystem 的主、绘制相机一致；Spectator `+0xC` 也必须指向该 FreeCamera。只有对象数量唯一不算通过。
3. 检查回放已暂停、控制器处于已验证自由分支、没有关联 Camera 组件，输入全部释放，位置、两组角度、FOV 持续稳定。FOV 当前等于目标只能排除数值上的差异，不能自动证明动画队列为空。
4. 保存标量快照：Camera 的 position、target、up、roll、interface/projected FOV、aspect；控制器的目标位置、目标/当前角度、方向、up、原生滚转量、FOV 当前/目标、模式与输入观测。view/proj/VP 用于核验，不当作唯一恢复来源。绝不把整个对象块或指针/引用计数/vtable 写回。
5. 人工移动并重新停稳，再读取第二份快照。用它确认目标位置与当前位置、方向与 target-position、投影与实际 FOV 的关系。若对象重建或模式改变，丢弃这次恢复候选。

### 5.2 后续经授权的单次恢复必须同时处理什么

以下仅是待执行设计，不含已执行的游戏写入：

- **位置**：恢复相机 position，同时把原生控制器目标位置对齐到同一位置。否则共同更新按旧目标继续平滑。
- **朝向**：恢复相机 target/up/roll，并恢复对应控制器的目标角度、当前角度、方向/up 和原生滚转量。对于保存时原生静止的快照，优先恢复当时成套值，避免首轮引入新坐标换算。
- **FOV**：恢复接口值及对应控制器当前/目标值；必须确认或安全结束待完成 FOV 动画。动画对象指针不能恢复，队列结构尚未研究到可以直接修改的程度。
- **输入**：要求物理输入已松开，清理/消费待处理增量必须按其生命周期设计；不允许为了方便把未知输入和模式字段整块清零。
- **缓存**：使用原生 setter/更新语义或经过验证的等价计算维护投影范围、矩阵与脏标志。直接写矩阵或“写几个数再写 flags”仍不是已经证明的安全方案。
- **提交时机**：成套状态必须在所属游戏更新线程的确定时机提交，随后让原生相机更新/矩阵构建执行；外部多次零散写入没有原子性保证。当前只读 API 不能提供这个事务能力，远程调用/Hook/注入均未在本文执行，也不属于当前既有授权。

首轮只验证“保存原生静止机位 A，人工移到 B，再恢复 A”，不同时改变空间范围、碰撞、灵敏度或模式。每次至少保持 60 个已识别渲染帧，核对 Camera 和控制器状态不再朝 B 回移，再核对静态地标。若只用异步读侧约 50 Hz 采样，应如实写“采样点持续一致”，不能改称逐渲染帧成功。

### 5.3 当前仍阻止宣称完整 A 成功的项目

1. 没有做过实际外部写回，无法证明控制权或终点保持。
2. 尚未确定可用于成套提交的已授权机制和线程时机。
3. 尚未完整解析 FOV 动画对象的存活/取消接口。
4. 尚未验证任意 up/roll 组合和超出原生俯仰范围的姿态；首轮不要将它们隐含进“机位恢复”。
5. 边界/碰撞函数、原生时间步来源以及其他场景切换写入尚需定向核验；当前更新链的存在不代表已枚举所有写入者。

因此，适合首版的是：先提供当前构建限定、严格回放校验、相机与原生控制器成套读取/保存/比较；恢复入口保持不可执行，直到上述具体写回实验获得授权并通过验收。此安排保存了已验证成果，也没有把只读验证冒充完整摄影控制。
