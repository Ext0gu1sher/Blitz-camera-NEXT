## 具体调用与生命周期证据

静态地址均为本构建的首选 VA，运行时使用实际模块基址重定位，不沿用旧进程地址。

- `0x013E5EA0`：`ECX=ReplayPlayer`，栈上传单个 `float delta`，`ret 4`。目标采用 `raw + delta`，而页面时间是 `raw - origin`。本轮计算 `delta = 用户目标显示时间 - 当前显示时间`，不把显示时间直接当 raw。
- `0x013E5B60 → 0x01409CA0`：回跳取消主更新信号中属于播放器的回调，清理记录读取/场景状态，排队重建任务。
- `0x006C35E0 → 0x006CD9C0`：移除信号节点时，`node+0x48` 的 bit 0 表示正在发送；此时只标记删除，延后释放。最小 Hook 在发送节点里执行，额外检查此 bit；恢复自己的回调指针后再调用原生跳转，不再访问旧节点。
- `0x01412C70`：重建任务清 token、调用初始化，再进入特殊快进。
- `0x013FF680`：约 0.1 秒步进处理记录；完成时恢复原倍率和暂停状态。不是逐帧精确落点接口。

- `research/builds/11.21.0.1235/replay-seek-minimal-17.txt`（清理、重建、完成、tick 包装器）。

## 可复用的实验入口

```powershell
# 只读检查：要求已进入自由镜头并暂停，页面轨迹停止
python -X utf8 -B tools/verify_replay_seek.py --delta 2

# 显式执行单次；最小试验限制前后 0.01–5 秒，绝对目标单位为页面显示秒
python -X utf8 -B tools/verify_replay_seek.py --target 70.3670244216919 --execute
```

`--execute` 是明确的运行时修改操作，不应作为只读命令执行。它加载自建、哈希锁定的 `replay_seek_trial_1121.a94b38b85e50.dll`，仅改现有 ReplayFunctor 的回调数据指针，在游戏更新线程恢复指针后执行一次已分析的原生入口。DLL 保留驻留，不卸载正在执行的代码。共享配置仅 156 字节，C/Python 布局、整块范围及加载后的可执行节均核对。Hook 超时/取消不能触发第二次请求。

7 组本地 x86 假对象验证通过，包括 thiscall float ABI、请求前撤销、节点销毁后无旧地址恢复、单次执行、取消、心跳失效、时钟变化、边界和暂停条件。Python 全套 176 测试通过（新增 5 项）。

## 下一步建议

原生回跳路线可继续，但当前只能称为“定位到目标附近”。同一目标的前跳落点受起始时间格点影响；本回放两次从头重建的落点相同，不能据此推广到任意时刻/回放或称为逐帧精确。

下一轮先验证“跳到目标前方的一小段 → 使用已有逐帧变速机制正向补齐剩余时间 → 暂停”，不回写 raw 强行对齐。需要测最后一帧 Replay 与 Scene 的有效 dt 是否一致、记录游标及坦克事件是否复现，然后把重新发现对象、切自由镜头、恢复机位串起来。只有这个闭环成立后，才适合给 UI 添加“回到拍摄起点”。
