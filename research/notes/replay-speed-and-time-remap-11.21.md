# 11.21 回放慢放、曲线变速与倒放研究

研究日期：2026-10-19。本轮只读分析安装文件与公开文档，未启动或操作游戏，未连接游戏进程、注入、写游戏内存或修改安装文件。新增内容仅为工作区中的研究脚本、解包证据与本记录。以下“确认”指当前二进制中的静态证据，不表示慢放、变速或倒放已经实测成功。

## 决策

**优先验证正向慢放，再实现连续速度曲线。** 当前客户端确有浮点播放倍率，以及把有效倍率传给动画和场景的原生通知链；这比模拟快捷键或反复修改时间值更适合拍摄。建议第一轮覆盖 1×、1/2×、1/4×、1/16×，通过后再扩大范围。

**向后跳转有具体代码入口，但连续倒放没有形成可用路线。** 已检查的向后分支会清理、重建回放，然后重新正向处理记录到目标时间。它不是负倍率播放。第一阶段将其视为“回到之前的拍摄起点”的候选功能，不能当作平滑倒放。

**如果目的只是成片倒放，先正向拍摄、再倒序视频最实际。** 游戏内随意拖动到过去、继续自由移动相机，是另一项能力，需要验证重建与寻址成本。

| 目标 | 目前证据 | 尚未证明的部分 |
|---|---|---|
| 固定正倍率慢放 | 正常 tick 将 dt 乘以 float 倍率；动画、场景有缩放链 | 当前回放中所有运动/特效是否一致减速，声音怎样处理 |
| 连续曲线变速 | 倍率不是档位枚举，通知传递的也是 float | 逐帧更新通知的成本、同帧顺序、新动画继承倍率 |
| 战斗暂停但镜头运动 | 本项目已有暂停运镜实验；原生暂停跳过普通回放推进 | 与变速功能组合后的生命周期；不能直接沿用只允许暂停的守卫 |
| 向后跳转 | 当前 EXE 有请求、清理、任务、重建、赶到目标、恢复状态的完整分支 | UI 是否开放，调用条件、重建耗时、落点误差和场景完整性 |
| 连续负倍率倒放 | 所检查路径没有逆向撤销事件的机制 | 不能由“float 能存负数”推导可用；不建议第一轮试负值 |
| 倒序成片 | 通用视频工具具有成熟的倒序处理能力 | 不能在倒序成片内重新选择游戏机位；音轨另行处理 |

## 1. 普通播放如何推进时间

`ReplayPlayer` 的字段名为研究标签：

| 相对偏移 | 含义及用途 |
|---|---|
| `+0x11` | 活动推进注册状态 |
| `+0x12` | 暂停 byte |
| `+0x14` | 播放倍率 float |
| `+0x18` | 原始回放时间 float |
| `+0x1C` | 已检查记录泵中的下一记录索引 |
| `+0x28` | 跳转目标，原始时间域；非零不表示正在跳转 |
| `+0x2C / +0x2D / +0x2E` | 向后方向 / 特殊推进活跃 / 特殊推进等待 |
| `+0x30 / +0x34` | 跳转前保存的倍率 / 暂停状态 |
| `+0x35` | 时间初始化有效标志 |
| `+0x64` | 时间原点 |
| `+0x108` | 待执行重建任务 token；`0xFFFFFFFF` 为无待执行任务 |

getter `0x013ECD90` 的公式是 `(initialized ? raw : 0) - origin`。初始化未完成时不能先把结果钳到零，再将其当作有效时间。

正常更新 `0x0140D100` 先检查特殊推进，再检查暂停。普通路径的关键指令：

```text
0140D13C  mulss xmm0, dword ptr [esi+14h]  ; dt × rate
0140D148  addss xmm0, dword ptr [esi+18h]
0140D15D  movss dword ptr [esi+18h], xmm0
```

之后限制时长上界、调用记录处理 `0x013FD6F0`，并在末端把缩放后的 dt 传给 `0x013E8BF0`。后者继续传给内部对象更新；本轮没有完整命名其所有下游。

这直接支持正倍率慢放的候选实现。**它没有证明 dt 等于现实帧间隔，也没有证明全部子系统只缩放一次。** 下一轮必须同时采集实际 dt、raw 增量和场景 dt，防止重复缩放或某些系统漏缩放。

记录泵 `0x013FD6F0` 依时间顺序消费记录，并在 `0x013FD8AA / 0x013FD8DA` 等位置增加 `+0x1C`。已处理的开炮、受击、死亡等事件不会因为 raw 减小就自动撤销。因此不直接写 raw 实现播放，不把负 rate 当成倒放。

## 2. 变速不是只改一个 float

`0x0140EC00` 为本轮识别的“传播有效回放倍率”例程，输入来自同一个 ReplayPlayer：

```text
effectiveRate = (paused ? 0 : 1) × rate
    → AnimationManager，组 0 的动画时间缩放
    → .replayPlaybackSpeedChanged 事件
        → GameSceneController 回调
            → GameScene 的时间缩放值
```

可复核的证据：

| 位置 | 实际行为 |
|---|---|
| `0x0140EC29–0x0140EC46` | 读 `+0x12 / +0x14`，计算有效倍率 |
| `0x0140EC60 → 0x0093EC70` | 遍历动画集合，筛选动画 `+0x3C` 分组，写 `+0x40` 时间缩放；此处传 group 0 |
| `0x0140ECD4` | 发送 token `0x046E8E0C` 对应的 `.replayPlaybackSpeedChanged` |
| `0x01E02DBD–0x01E02DD9` | GameSceneController 将 `0x01E17820` 注册为该事件回调 |
| `0x01E17820 → 0x007C2F00` | 提取 float，向 controller `+0x1C` 指向的 Scene 写 `+0x2A8` |
| `0x007C46F0`，尤其 `0x007C4701` | Scene 更新在 `+0x2A4 != 0` 时将输入 dt 乘 `+0x2A8`，再调用 `0x00D72810` |

Scene 缩放开关也有独立条件：构造片段 `0x007B3129–0x007B312C` 将第六参数写入 `+0x2A4`；创建调用 `0x017733E5` 的此参数来自上下文虚调用 `+0xA8`。在 AvatarContextReplay 的表 `0x037F8A00` 中，该槽是 `0x01761220`，它调用 `+0xAC`（`0x007BD830`，读取上下文 `+0x1B8`）并判断返回值是否非零。**下一轮应实测开关为 1，不能仅观察 Scene 倍率字段写成功。** 此处没有把尚未确认的 `+0x1B8` 对象直接命名为某个系统。

另一个已找到的订阅回调 `0x01D5E340` 将提取的 float 写入接收对象 `+0x5C`。本轮未可靠命名该对象，也未证明已找全订阅者。不能把它推断成音频变速接口。

没有找到可直接称为 `SetPlaybackSpeed(float)` 的已验证通用入口。已找到的通知调用点主要属于初始化、清理、暂停与跳转。候选做法是：**在经验证的游戏主线程更新边界设置 ReplayPlayer 倍率，然后调用原生通知例程**。这不是现在已可调用的公开 API，也不在本轮执行。

逐帧连续变速还有两个待查点：现有动画是遍历后设置倍率，新创建动画是否继承；每帧发送事件是否产生重复工作或可见重置。常量倍率通过后，才能评估通知成本并决定是否需要更窄的适配。

暂停 setter `0x01402000` 修改 `+0x12`、传播有效倍率，并发送 `ReplayPlayStatusChanged`。**rate = 0 不等于调用暂停。** 拍摄中的完全停格优先使用原生暂停，再由独立拍摄时间决定恢复；暂停时保存的 rate 仍为 1 是正常情况。

## 4. 向后跳转的实现与倒放边界

相对时间请求入口 `0x013E5EA0`：检查活动状态与特殊推进状态，把 `current raw + delta` 限制在合法时间范围，保存原倍率与暂停状态，然后选择前进或向后分支。向后请求还有接近回放末尾约 3 秒的拒绝分支，边界行为需实测。

已闭合的向后路径：

```text
0x013E5EA0：计算目标、保存 rate / pause
  → 0x013E5B60：RewindStarted、清理当前推进
  → 0x01409CA0：清理
  → 0x0091D090：排队延后任务，token 写 +0x108
  → 回调 0x01412C70：清 token、调用 0x01408AD0 重建
  → 启用特殊推进 +0x2D
  → 0x013FF680：正向处理记录，赶到目标
  → 恢复 rate / pause，发 RewindFinished
```

特殊推进临时使用 rate = 1，并解除暂停；循环以约 `0.1` 秒增加 raw，更新相关子系统。记录处理需要等待时设置 `+0x2E`。这意味着它可能有时间步进带来的落点误差，**本轮没有证明落点逐帧精确，也没有测量重建耗时**。

跳转完成不是单一 flag 的原子事件：任务 token 在初始化前已经清除；`+0x2D` 也可能在原倍率、暂停状态恢复完成前清除。需要综合任务状态、active、initialized、暂停状态、时间域和对象链，等待稳定后才能重新接管镜头。

技术判断：

- 单次向后定位：有具体可验证路线，用于重复拍摄值得继续。
- 持续拖动时间轴：应合并/延迟请求，等上一轮重建结束；不能每次鼠标移动都请求重建。
- 每帧向后 seek：现有机制的重建成本与时间粒度都不适合直接承诺平滑效果。
- 负倍率：已检查的记录泵只有前向消费，不具备撤销事件能力；不能只改倍率为 -1。
- 全状态快照：需要覆盖对象、事件索引、动画、粒子、随机状态、异步加载等；尚未找到可用的完整序列化接口。仅拷贝几块内存无法证明能恢复整个场景，维护成本高，后置。
- 视频倒序：适合直接得到倒放镜头。正向拍摄时预先反转镜头轨迹的时间安排，再倒序视频，可得到所需最终镜头方向；非线性变速需连时间映射一起反转，不能只交换 A/B。

官方帮助仍写前进时间轴、无倒退，并解释回放是由客户端重建的技术记录，版本需要匹配。这是公开操作能力的说明，不能覆盖本机 EXE 中尚未验证的重建分支。来源：[Wargaming 回放帮助](https://www.wargaming.net/support/en/products/wotb/article/16386/)，访问 2026-10-19；页面没有给出对本机 11.21 构建的功能认证。

视频后处理可参考 [FFmpeg reverse 官方文档](https://ffmpeg.org/ffmpeg-filters.html#reverse)，访问 2026-10-19。该滤镜需缓冲整段，短片段先裁剪再倒序更合理。本轮未处理或导出用户的视频。

## 5. 曲线变速如何与镜头轨迹组合

保留两个时间：拍摄时间 `s` 和战斗回放时间 `t`。用单调时间映射 `t = T(s)` 设计速度，倍率为 `dT/ds`。第一阶段仅允许正倍率；停格用明确的暂停段。

例如一段 8 秒成片：

| 拍摄区间 | 播放倍率 | 理论战斗推进 |
|---|---|---|
| 0–2 秒 | 平滑从 1× 降到 1/4× | 1.25 秒 |
| 2–6 秒 | 保持 1/4× | 1 秒 |
| 6–8 秒 | 平滑从 1/4× 升到 1× | 1.25 秒 |
| 合计 | 两侧采用对称 smoothstep | 3.5 秒 |

这是数学设计值，不是游戏测试结果。

镜头可以选择：

- `Camera(s)`：镜头在 8 秒里正常走完，战斗只发生 3.5 秒。适合围绕慢动作、定格目标运镜。
- `Camera(t)`：镜头跟着战斗时间一起慢下来，暂停也一起停。适合固定在某个战斗事件节奏上的运动。

轨迹的空间形状、镜头速度曲线、战斗速度曲线必须分开。空间匀速仍需弧长映射，不能用均匀样条参数代替。

实现应在游戏更新线程按帧求值，网页只负责提交整条曲线和播放命令。不要由网页定时器每隔几十毫秒写一次速度。先确认实际 dt 的来源与调用顺序，再使用本帧的时间映射增量；若 dt 可用，候选倍率为 `(T(s+dt)-T(s))/dt`，避免掉帧改变曲线积分。实际 raw 增量持续回读，误差通过有限的后续倍率调整或中止本次拍摄处理，不能跳写 raw 追赶。

首轮不承诺任意低倍率。raw 为 float，极慢时每帧增量可能接近该时间值的浮点分辨率；记录插值、特效更新和音频还可能有更早的限制。先验证 1/16×，再探索更慢。

## 6. 下一轮最小验证，按顺序执行

本节是后续实验方案，不表示本轮已获授权并执行运行时变更。等用户重新打开当前版本本地回放后进行。

### T0：确认同一帧里谁先更新

固定镜头，选能看见坦克运动和开炮的短片段。记录 ReplayPlayer tick 的线程、输入 dt、rate、raw/origin、暂停/seek 标志，Scene 更新的输入/输出 dt、`+0x2A4/+0x2A8`，以及动画和 Draw 的顺序。

仅外部采样不足以证明每帧顺序；若需在入口加观测 Hook，它属于后续运行时实验，不能称为纯只读附件。先优先利用现有可记录的更新边界，再决定新增观测点。

通过标准：1× 时回放时间推进与实际输入 dt 对应，原生暂停时普通时间停止；Scene 缩放开关有效；知道倍率修改应放在哪个线程和哪一帧阶段，避免同一帧部分系统用旧倍率、部分用新倍率。现有相机 Hook 所处位置不能未经核对就当成合适的变速入口。

### T1：固定 1/4×，先看战斗是否完整慢下来

暂停保存起点与原 rate/pause；通过主线程命令设置 `0.25`，调用原生通知，再解除暂停。镜头位置、朝向和 FOV 全部固定，不同时测试运镜。

运行约 8 秒后恢复原倍率并暂停。记录整个过程，并检查坦克、履带、炮弹、爆炸/烟尘、阴影与音轨。

通过标准：约 8 秒的正常帧时间对应约 2 秒战斗时间；精确检查以 `sum(dt × rate)` 与实际 raw 差值为准，允许首尾帧和 float 量化，不能仅看 UI 整秒数。每帧数值误差与按相同 float 运算计算的预期相符，不出现持续增长或一帧使用两种倍率的现象；画面持续渲染，关键运动没有一部分仍按 1× 播放。之后按同法测 `0.5` 与 `0.0625`，8 秒分别预期约 4 秒和 0.5 秒。

失败排查：只有计时变慢则查通知是否完整、Scene 开关、动画分组；整体变成倍率平方则查重复缩放；新爆炸突然正常速度则查新建动画/粒子继承；声音未缩放则先界定为需独立处理的音频范围，不能宣称全部媒体同步。

### T2：8 秒连续曲线

执行上文 1×→1/4×→1× 的 8 秒曲线，理论战斗推进 3.5 秒。第一遍保持固定相机，第二遍从同一战斗时刻重放。

通过标准：倍率和时间增量连续，事件顺序与正常回放一致；没有按档位突跳、新事件速度突变或阴影重置；通知调用时间不造成新增卡顿。两次按战斗时间对齐后关键事件一致。像素完全相同不是本阶段承诺，粒子随机性与渲染历史需单独测量。

### T3：接入既有镜头轨迹

先用 `Camera(s)`，再用 `Camera(t)`。当前相机实现的“只允许暂停回放”约束需要新增明确的受控播放模式，保留回放身份、对象一致性、seek/加载状态检测；不能只删掉 paused 检查。速度调节在适当的模拟阶段完成，镜头仍在已验证的相机更新阶段接管。

通过标准：战斗慢放时镜头按指定拍摄时间完成；同步模式按战斗时间完成；暂停段可继续或停止镜头，符合所选模式；停止后恢复原倍率/暂停状态及关联时间缩放。如果对象换代，停止对旧对象操作，不强行“恢复”旧地址。

### T4：单次向后定位，独立于连续慢放

先停止并解除相机接管。避开开头、末尾与加载阶段，试一次短距离前进，再试向后约 1–2 秒，使用已查到的原生相对跳转请求。

观察重建任务、特殊推进、原点和对象变化、记录索引，以及完成后的落点误差、血量/死亡/弹道状态。记录实际耗时；不要预设它瞬时完成。完成后重新获取相机链并等待稳定，最后再恢复拍摄机位。

通过标准：每次请求只执行一次，重建确实结束，目标附近场景状态正确，原倍率和暂停状态恢复；重复拍摄的落点误差有明确可测范围。若误差不满足拍摄要求，先采用较早锚点加正向精确推进；若原生分支不可用，回退到重新打开回放并正向推进。不开启每帧 seek 或负倍率试验。

## 7. 未解决问题与适配成本

- 未证明声音能随任意倍率变速，不能把已找到的 float 接收者直接命名为声音控制。
- 未证明所有新创建动画、粒子、物理/插值更新都继承连续变化的倍率。
- 未测原生向后跳转可用性、重建耗时和落点精度。
- 没有找到完整场景快照/反向事件求值接口。
- UI 资源事件与真正播放倍率不同；本轮找到的 UI 事件回调为空。
- 客户端升级后须重核 tick、通知、事件绑定、动画/Scene 字段、暂停/seek 生命周期与 Hook 顺序。曲线数学、关键帧格式和镜头时间域可以复用，地址与对象布局不能直接沿用。
- 这是非公开内部实现适配，不是官方摄影接口；本地回放用途本身不代表运营方已许可这类运行时扩展。

本轮没有改动现有相机/UI 产品功能，也没有把离线代码验证等同于游戏实测。下一项决定可行性的实验是 **T0 后的固定 1/4×：不仅时钟变慢，战斗画面各部分也必须按相同比例推进**。
