# 坦克跟踪与运镜预设可行性研究

日期：2026-10-25（Asia/Shanghai）。范围：更新上游参考源码、追踪实现、核对本项目接口、运行现有离线验证。没有新增跟踪功能，没有连接或操作游戏。本文中的方案是研究建议，不是已经实现的能力。

## 结论

在现有回放拍摄工作流中，坦克跟随、持续看向目标、相对车体的追拍，以及环绕、侧拍、推拉等预设均有明确实现路径。可以复用已经具备的回放车辆姿态、时钟换算、离线预览和游戏内绝对镜头播放链路。第一阶段无需重新逆向全套车辆数据，也不需要依赖画面识别。

近距离贴车、炮塔或炮口特写可以进一步研究，但目前证据不支持承诺与游戏实际渲染逐帧、像素级一致。若离线重建误差超过拍摄要求，再考虑读取游戏内目标最终显示姿态，作为精确模式。真实在线对局的即时跟踪是另一项适配工作，本次没有验证。

## WotbTools 的跟随到底做了什么

固定版本源码：[playbackScene.js](https://github.com/A158Coke/WotbTools/blob/612a9595828ff659393372805d3a9ee30d23d54f/frontend/src/scene/playbackScene.js#L3051)、[Replay3DPane.vue](https://github.com/A158Coke/WotbTools/blob/612a9595828ff659393372805d3a9ee30d23d54f/frontend/src/components/Replay3DPane.vue#L123)。

1. 名册行调用 `setFollow(eid)`，场景保存 `FOLLOW_EID` 并切到 follow 模式。点场景里的坦克主要负责选择和详情，选择与跟随分别管理。
2. `posAt` 从回放姿态采样器取得目标位置。首次进入时把 OrbitControls 的旋转中心放在车辆上，较远时收拢到约 26 米，并设置至少高于目标 9 米的入场高度。
3. 后续按目标的位置差，等量平移 `camera.position` 和 `controls.target`；用户仍可调整环绕角度、距离和构图。
4. 目标不可见时清空 `followAnchor`，再次可用时重新初始化。

因此它是浏览器三维回放中的位置跟随。跟随计算本身不使用车体 yaw 来旋转相机偏移，也没有在这段链路中提供游戏进程摄像机输出、目标部件约束或可保存的拍摄预设。坦克拐弯时，既定世界方位不会自动变成坦克的新后方。

值得借鉴的是目标选择、姿态查询与显示控制的分离。我们的拍摄轨道应按绝对时刻直接求值，不照搬逐帧累计位移作为工程数据，以便倒拖、跳转、变速和重复拍摄可以复现。

当前回放模式编译以 120Hz 采样，原生表容量 16,384 点，单次回放拍摄区间限制 0.5–120 秒。它是镜头输出采样密度，不代表回放原始车辆数据有 120Hz 的真实观测精度。密集的烘焙结果也不应直接塞入目前最多 200 个不同时刻的用户关键帧。

## 建议的镜头模型

先将“相机在哪里”和“镜头看哪里”分开：

- 位置：绝对路径，或目标位置 + 世界方向偏移，或目标位置 + 车体方向旋转后的局部偏移。
- 视线：手动关键帧，或持续指向目标锚点，并允许构图偏移。
- 预设：给相对距离、高度、方位、注视点、FOV 等参数随时间的变化方式；最后统一输出已有的绝对位置、姿态和 FOV。

概念公式为 `camera(t) = targetPosition(t) + targetRotation(t) × offset(t)`，视线由相机指向目标锚点。具体计算必须先统一坐标系：回放为 y-up，本项目摄像机为 z-up，Three 场景还对 x 做镜像，不能直接混用数值。

普通追拍默认只继承车体水平朝向、保持地平线；完整继承俯仰和侧倾可作为车载感选项。车体前方与速度方向不同，倒车和原地转向时尤其需要明确区分。

| 候选能力 | 可行性判断 | 主要新增工作 |
| --- | --- | --- |
| 固定相机持续看向一辆车 | 高 | 目标选择、注视锚点、方向求值与角度连续性 |
| 按原有绝对路径移动，同时锁定目标 | 高 | 将位置轨道与朝向约束组合 |
| 车后追拍、车侧并行、前方倒拍 | 高 | 车体局部偏移、水平稳定、距离和高度参数 |
| 围绕行驶车辆环绕、升降、推进拉远 | 高 | 参数曲线、过渡与预设保存 |
| 暂停坦克而镜头继续环绕 | 高 | 车辆按冻结的回放时间采样，运镜参数按拍摄时间推进 |
| 炮塔/炮口特写与固定画面构图 | 有条件可行 | 部件锚点、准确的车型装配、构图约束及实机误差测试 |
| 游戏内每帧紧贴实际显示模型 | 需要额外研究 | 全车辆身份到 TankVisual 的可靠映射、最终变换和更新时序验证 |
| 自动避墙、避地形、自动保持无遮挡 | 独立的后续功能 | 碰撞/遮挡检测与镜头选择，不能由跟随公式自然得到 |

第一阶段推荐复用 JS 车辆采样器，在指定工作区内生成已求值的镜头表，经过后端校验后交给现有原生播放器。工程仍保存可编辑的目标和相对参数，生成表作为缓存。换回放、时间微调、机位、目标、参数或解析版本时必须失效重建，预览与实机消费同一套求值语义。

接入时要注意 `compile_positions` 在原关键帧时刻优先使用 `keyframe.pose`：如果只改变 `sample(t)` 而保留旧关键帧姿态，这些时刻会回到旧朝向。编译入口与关键帧姿态必须统一为最终镜头求值。本文只指出集成条件，未修改编译器。

## 精确跟踪的真实限制

### 平滑重建不是实际渲染的逐帧真值

[trackInterp.js](https://github.com/A158Coke/WotbTools/blob/612a9595828ff659393372805d3a9ee30d23d54f/frontend/src/scene/trackInterp.js#L1) 明确说明 `pose_kf` 是显示重建，段首使用约 0.2 秒稳态延迟，目的是避免低频采样与位置更新不同相导致抖动。文中“≤1cm/0.2°”描述相对重建帧的压缩/插值误差，不是与真实游戏模型的对齐误差。

不能再人为给所有目标固定补偿 0.2 秒；已有重建已包含处理，必须先测量实际剩余误差。贴车镜头会放大位置误差，炮口特写还叠加装配、车体/炮塔旋转、炮管俯仰和未还原动画的影响。

若确实需要更高精度，可研究从游戏当前帧的目标显示变换求镜头。现有赛事实验只证明特定虚拟车的 `VehicleGameLogic → TankVisual` 身份链，没有证明任意车辆的最终世界变换已经可靠取得，也没有验证在现有相机更新回调中读取它的时序。因此这是有线索的下一阶段，不能宣称已经完成。

### 数据缺口与生命周期

单份回放只包含该录制视角获得的数据，目标不在数据覆盖范围时不能保证连续真实跟踪。这里的可见/在场区间不应一概命名为服务器全局点亮状态。

- 缺数据时明确选择保持最后构图、切回绝对路径或停止该跟踪区间；重新出现时做有定义的过渡。
- 按回放身份、账号和当前实体区分目标，处理死亡、残骸滑动、重新出现及重生，不能只持久化一个内存地址或把实体 ID 跨回放复用。
- 已有双方回放合并实验在一个样本中补齐了运动覆盖，可帮助后续拍摄；它仍是实验路径，不代表任意回放都能恢复全场信息。
- 平滑应可按时间重算或预先烘焙，避免依赖上一次播放经过的路径。暂停、倒拖或切换倍速不应改变同一时刻的构图。

## 本轮验证与下一步验收

本轮运行：

- `python -B -m unittest tests.test_replay_preview tests.test_replay_clock`：17 项通过，包括已有姿态、炮管方向和时钟相关验证。
- `tools/verify_replay_pose.mjs` 使用现有真实 FVE Defender 回放项目副本：14 辆车、3,479 个采样时刻、44,470 次车辆状态采样。姿态有限、关键点严格递增、正向/反向查询一致，解析输入与原回放哈希未改变。
- 报告：`output/tracking-research-20261025/pose-verification.json`。

上述验证证明现有采样基础可以复用，没有测试尚未实现的跟踪功能，也没有比较真实游戏逐帧画面。此真实回放脚本调用的是不带车型俯仰限制参数的解析入口；炮管方向相关验证来自既有定向测试，不能把这次整段采样检查当成炮口精度验收。

建议按以下顺序推进：

1. 先完成单目标持续注视、世界偏移跟随、车体朝向跟随，使用同一目标采样及镜头求值规则。
2. 接入单机位/多机位保存、区间启停、失去目标和重新捕获策略，再提供车尾、侧拍、环绕、推拉预设。
3. 选直行、急转、倒车、斜坡、进出数据覆盖范围及阵亡滑动片段，在不同距离/FOV、暂停/变速/跳转下验证；分别记录世界位置误差和目标屏幕构图误差，报告中位数、95 分位及最大值。误差阈值按镜头用途确定，不在没有实测时承诺厘米或像素精度。
4. 基础跟踪误差可接受后进入部件特写；若达不到要求，再以精确客户端构建为边界研究实时显示变换读取与镜头更新同步。

本次没有更改产品源码、打包产物或原项目文件；主仓库开始时已有的多机位等未提交修改保持原样。

## 补充：其他物体与精度量化

同日继续研究，直接读取实际使用的 Agent v0.4.11 固定提交源码，而不是只依赖前端注释。

### 对上一节误差描述的补正

前端 `trackInterp.js` 注释提到的“≤1cm/0.2°”不可作为当前解析器阈值。当前 [playback.rs:54](https://github.com/fanypcd/WoT-Blitz-Agent/blob/0a9da93a0074a95af406db3468e6a81a5a6b139f/crates/replay-core/src/replay/playback.rs#L54) 实际设置 `KF_TOL_POS=0.02m`、`KF_TOL_ANG=0.007rad`（约 0.40°）。这是相对内部重建帧的折线压缩容差，落盘还包括位置 0.01m、角度 0.001rad、时间 0.0001s 的舍入。相关合成测试允许位置误差 `0.02+0.006m`；它不是对任意真实游戏画面的 2.6cm 保证。

目前没有采集目标游戏最终渲染变换与跟踪相机的同帧对照，因此实际跟踪误差的中位数、95 分位和最大值均未知。上一轮 44,470 次状态检查证明数据有效与重复求值一致，不证明厘米级实机精度。

### 其他目标

- **建筑、桥梁、水塔、地形锚点**：本项目地图导出器 `world_transform` 已读取客户端场景的世界位置、旋转与缩放。可以指定建筑实例，或通过表面拾取选择墙角、窗户等锚点。静态目标没有运动延迟误差，通常最适合首先做到稳定锁定；仍须核对地图版本、实例、坐标转换和几何精度。建筑被毁后的碎片不能自动沿用原静态锚点当作动态轨迹。
- **普通炮弹**：已有发射点、终点、速度以及跳弹/穿透续段，`shotPath.js` 按分段直线、段内匀速求值。可以跟随这条重建路径，但尚未证明它等于游戏每帧实际弹体的位置。包时钟不是精确飞行时长。
- **制导导弹**：本次检查的播放接口与采样器没有证明一条完整的制导转弯轨迹；不能凭 `atgm_heat` 弹种分类或普通炮弹折线就声称支持。若客户端存在可读取的弹体最终变换，可以研究直接绑定；若依赖离线回放，须先识别转向/运动数据与生命周期，再实现重建。
- **飞出炮塔**：Agent 已有 `detached_turrets`，提供实体 ID、所属车辆、覆盖区间和原始 Type5/Type10 位置及三轴姿态。这类动态刚体有明确扩展路径，但插值与实际客户端显示仍需对比。
- **倒树、可破坏物和碎片**：WotbTools 能把破坏事件关联到地图实例，倒向字节步进为 1.40625°。其 `destructibles.js` 明确将倒树运动描述为刚性旋转近似，未还原完整关节弯曲及邻树碰撞，不能据此精确跟踪树梢、飞散碎片。烟雾等粒子也不应默认存在可持久识别的逐粒子轨迹。

### 高速弹体的额外限制

[playback.rs:901](https://github.com/fanypcd/WoT-Blitz-Agent/blob/0a9da93a0074a95af406db3468e6a81a5a6b139f/crates/replay-core/src/replay/playback.rs#L901) 将 `t_fire`、`flight_secs`、`leg_secs` 通过 `r2` 保留到 0.01 秒。单个时刻的最近舍入偏差可达约 0.005 秒；假设弹速 1000m/s，仅这个时刻量化就对应约 5 米的沿轨迹偏移。飞行时长也被舍入，不能把 5 米当作整个流程的误差上界。直射飞行时长另有 0.02–8 秒截断以及速度无效时 0.5 秒回退，都不适合作为高精度追弹的权威输入。

### 具象表达（数学示例，不是实测）

1920 像素画面宽度、水平 FOV 60°、目标接近画面中心，在同一深度下产生横向位置误差时：

| 距离 | 横向误差 2cm | 横向误差 10cm | 横向误差 50cm |
| --- | --- | --- | --- |
| 10m | 3.3px | 16.6px | 83.1px |
| 30m | 1.1px | 5.5px | 27.7px |
| 100m | 0.3px | 1.7px | 8.3px |

计算为 `pixels = width / (2*tan(horizontalFov/2)) * lateralError / depth`；小角度情况下也可用于解释镜头瞄准偏差。相同构图的 4K 输出像素偏移翻倍，实际屏幕占比不变；更长焦、更近距离会放大偏差。

时间错位的沿运动方向偏差约为 `speed * delay`：15m/s 的车辆错一帧（60fps，16.7ms）约 25cm；1000m/s 的示例弹体错一帧约 16.7m，错 1ms 也有 1m。转成画面偏移时只计横向分量，不应把沿视线运动的全部距离直接当作横向误差。

高精度模式建议以游戏实际显示变换和相机同帧同步为主要研究方向：先静态锚点标定，再车辆/部件，再高速弹体。以目标锚点相对设定构图的屏幕偏移作为主要验收指标，搭配世界坐标误差与时间偏差；例如“1080p 下 95% 帧不超过 2px”可以是事先约定的目标，但尚不是当前实现的结果。
