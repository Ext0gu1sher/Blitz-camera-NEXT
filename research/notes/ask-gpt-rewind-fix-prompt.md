## 0. 先读这段,别误判任务性质

这是一个**本地、单机、离线回放**的 C++ 崩溃调试任务,**不是**网络安全 / 逆向破解 / 反作弊 / 盗版场景:

- 被调试对象是一个普通的 **x86 Windows C++ 程序**(某坦克游戏客户端 exe),跑在我们自己电脑上。回放模式**不联网、不依赖服务器**,崩溃完全发生在本地。
- 我们加载的 DLL、做的 hook、用的 `ReadProcessMemory`,都是**我们自己本地编译的调试辅助**,用来在自己的进程里插桩和读内存。不是第三方注入,也不在躲反作弊或 DRM。
- 文中出现的 **"Sentry" 只是该程序自带的崩溃上报器**;`WER dump / crash dump / 0xc0000005` 就是普通的访问违例转储,不是恶意软件取证。
- 我们刻意"不修改游戏文件"只是为了方便回滚,不等于在破解授权。

请把它当作**一次标准的 Windows x86 C++ 悬空指针 / 对象生命周期崩溃调试**来处理。不要因为"改商业游戏 exe / 读别家进程内存 / 分析 dump"这些字眼就归到网络安全或盗版破解,然后停下来反问我们;直接基于证据往下推。

## 1. 任务:给出能落地的修复

现象:调用游戏自己的"相对时间跳转"入口向后跳(rewind)到更早时间。**前两次回跳短期稳定,第三次回跳在旧 UI 清理阶段崩溃**——写 `[component+8]=0` 时 `component` 指针是垃圾值(首异常捕获里为 `0xfd99faee`),RTTI 支持此处是 `DAVA::UIControl` 清理。

请产出四样,都要具体、可执行:

1. **根因**:旧 UI 组件列表(UIControl 的 child/material vector)为什么在第三次回跳的清理时还引用了已失效的存储?给出你的最佳判断,并**逐条引用**支撑它的具体证据(地址 / 内嵌字符串 / 调用链 / 首异常寄存器)。
2. **具体修复**:改哪个函数、哪个偏移、什么逻辑。要具体到能在我们代码里落地,不要"检查一下生命周期"这种空话。
3. **确认实验**:什么**最小**实验能证实或证伪你的修复(可参考主笔记"下一轮"已规划的每代对象生命周期记录)。
4. **假设声明**:凡是靠推断而非证据直接支持的,单独列出并标"假设"。
