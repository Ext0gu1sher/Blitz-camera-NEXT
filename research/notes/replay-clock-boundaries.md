# ReplayPlayer 时钟、跳转边界与只读保存门禁

研究日期：2026-10-14。对象仅为本机 Steam `11.20.0.887`：

- 文件：`C:\Program Files (x86)\Steam\steamapps\common\World of Tanks Blitz\wotblitz.exe`
- SHA-256：`4813544d3d6b9f45a357e87f5a14d065bd108c4acd324ac1506cb6d1ad6ff0af`
- PE32 / x86，首选映像基址 `0x00400000`。
- 本文代码地址均为**首选 VA**；RVA = VA − `0x00400000`，运行时必须重新加实际模块基址。它们是此构建的证据位置，不是可跨版本调用的 API。

本次补充仅静态读取 EXE；反汇编工具只在分析 Python 自身进程映射非执行字节。未读取游戏进程、未操作 UI、未注入或修改游戏。运行数据全部来自此前已保存的只读证据，不是本次新实测。

## 已确定的结论

当前 EXE 有可从内存读取、无需 OCR 的回放时间和跳转状态。时间 getter、正常推进和快进/重建路径能够静态闭合。`+0x28` 是残留也合法的跳转目标；真正的执行门是 `+0x2D`。`+0x2E` 表示特殊推进遇到需要等待的条件；`+0x108` 标识已排队、尚未执行的重建任务。

因此，“有一个有限的 `raw - origin` 值”不足以允许保存：停止/清理、向后跳转排队、重建初始化、快进以及快进完成后的状态恢复，都可能暴露看似正常的时间值。第一版应只接收确认活动、暂停、初始化完成且无跳转的稳定采样。

静态证据不等于已验证用户界面的所有播放/变速/重播路径。本轮没有播放、变速、跳转的时序实测，也没有证明外部采样与某一渲染帧原子对应。

## 字段证据表

基址为经对象链与 RTTI 验证的 `ReplayPlayer`。主 vtable 首选 VA `0x036EB15C`，对象 `+0x0C` 的次 vtable 为 `0x036EB164`。字段名字是根据指令语义给出的研究标签；没有原始私有类头文件。

|---|---|---|---|
| `+0x11` | byte | 初始化 `0x013CAC32` 置 1；清理 `0x013CB320` 清 0 并取消推进注册、释放数据。可称“活动推进注册状态” | 要求 1；时间初始化标志不能代替它 |
| `+0x12` | byte | 暂停状态；正常推进 `0x013CE689` 检查，非零直接返回 | 暂停保存要求 1；未来播放路径允许 0，但必须另做动态验证 |
| `+0x14` | float | 正常推进中与传入 dt 相乘；特殊推进临时改成 1，完成后恢复 | 记录当前速率；不能把它当作镜头速度 |
| `+0x18` | float | 原始回放时间；正常路径按 dt × rate 累加 | 和 `+0x64` 一起构造时间 |
| `+0x28` | float | 跳转目标，处于原始时间域；请求中由 current raw + delta 计算并限制范围 | 仅诊断，**不能以非零判定跳转** |
| `+0x2C` | byte | 请求 `0x013A92C9` 保存目标在当前之前的判断，选择 Rewind 分支 | 是方向/分支状态，不能单独当作正在跳转 |
| `+0x2D` | byte | 特殊推进活跃门；正常 tick 先检查它；快进/重建启用，完成时清零 | 非零立即拒绝保存、停止同步段 |
| `+0x2E` | byte | 特殊推进等待状态；处理返回 1 时置位，准备回调清除 | 非零立即拒绝保存、停止同步段 |
| `+0x30` | float | 请求时保存原速率，完成时恢复到 `+0x14` | 诊断；不是四个 bool |
| `+0x34` | byte | 请求时保存原暂停状态，完成时经暂停 setter 恢复 | 诊断；不能代替实时 `+0x12` |
| `+0x35` | byte | getter 是否采用 raw 的门；重置清零，特定记录到达后置一 | 必须为 1，否则不能报告有效的零起点时间 |
| `+0x36` | byte | 准备回调置一，记录类型 `0x11` 的处理据此决定继续或等待 | 可记录为附加准备证据；本轮未完整命名其生命周期 |
| `+0x37` | byte | 记录类型 `0x11` 处理时置一，正常 tick 末端清零 | 只记录；不能未经验证硬编码为“正在加载” |
| `+0x64` | float | 时间原点；初始化扫描记录类型 `0x11` 并取其时间 | 会话时间域的一部分，变化应使同步段失效 |
| `+0xA0` | pointer | 回放数据对象；清理函数清零 | 要求有效且属于当前已确认对象链 |
| `+0x108` | uint32 | 重建任务 token，`0xFFFFFFFF` 表示无待执行任务；排队后保存返回值，回调入口清回 sentinel | 非 sentinel 拒绝保存；覆盖向后跳转的排队阶段 |

## 1. 时间不是无条件的 raw − origin

getter 首选 VA `0x013B1BC0` / RVA `0x00FB1BC0`：

```text
013B1BC4  cmp byte ptr [ecx+35h],0
013B1BC8  jne 013B1BDB
           ... fld 0 ; fsub dword ptr [ecx+64h] ...
013B1BDB  movss xmm0,dword ptr [ecx+18h]
           ... fld raw ; fsub dword ptr [ecx+64h] ...
```

实际公式为：

```text
relative = (initialized ? raw : 0) - origin
```

特别是 `initialized == 0` 时，结果是 `-origin`，并非总是 0。第一版已拒绝 `+0x35 != 1` 的方向正确；不能先把负数钳到零再宣称有效。

正常 tick `0x013CE660` / RVA `0x00FCE660` 的关键顺序：

```text
013CE66B  cmp byte ptr [esi+2Dh],0
013CE66F  je  013CE689
013CE671  cmp byte ptr [esi+2Eh],0
013CE675  jne return
013CE67B  call 013C5C20            ; 特殊推进
           return
013CE689  cmp byte ptr [esi+12h],0
013CE68D  jne return              ; 暂停时跳过普通推进
013CE693  cmp byte ptr [esi+35h],0
013CE69C  mulss xmm0,[esi+14h]     ; dt * rate
013CE6A8  addss xmm0,[esi+18h]
013CE6BD  movss [esi+18h],xmm0
```

随后 `0x013CE6CF` 取得回放时长，`0x013CE6E6–0x013CE6EA` 将 raw 上限限制在时长；`0x013CE6F1` 调用记录处理 `0x013C4B70`。这支持正常播放的时钟设计，但传入 dt 与现实秒、各 UI 速率档位及渲染节奏的关系仍须时序实测。

暂停 setter `0x013C9190` 在 `0x013C91A7` 更新 `+0x12`，随后通知 `0x013CFCB0`。后者在 `0x013CFCD9–0x013CFCF1` 计算 `(paused ? 0 : 1) * rate`，并传至引擎相关速度通知路径。这里明确区分“保存的倍速”与“暂停后的有效推进速度”：暂停时 rate 保留 1 是正常的。

## 2. 快进和向后跳转如何改变时钟

请求入口 `0x013A9220` 接收相对偏移，先检查 `+0x11 != 0` 且 `+0x2D == 0`。核心指令：

```text
013A928F  addss xmm3,xmm4          ; current raw + requested delta
013A92A9  movss [ebx+28h],xmm0     ; clamp 后保存目标
013A92C3  seta cl                 ; 当前 > 请求目标
013A92C9  mov [ebx+2Ch],cl         ; rewind 分支
013A92DF  mov eax,[ebx+14h]
013A92E2  mov [ebx+30h],eax        ; 保存 rate
013A92E5  mov al,[ebx+12h]
013A92E8  mov [ebx+34h],al         ; 保存 pause
013A92FC  call 013A90C0            ; 向后跳转：排队重建
```

前进分支在 `0x013A930D` 用一次 word 写入令 `+0x2D = 1`、`+0x2E = 0`，触发事件并调用 `0x013C5C20`。事件 TypeDescriptor 的可读名字直接支持此判断：

| 首选 VA | EXE 内嵌名称 |
|---|---|
| `0x040CB620` | `.?AUFastForwardStarted@Avatar@GES@@` |
| `0x040CB64C` | `.?AURewindStarted@Avatar@GES@@` |
| `0x040CB674` | `.?AURewindFinished@Avatar@GES@@` |
| `0x040CB69C` | `.?AUFastForwardFinished@Avatar@GES@@` |
| `0x040CB6F8` | `.?AUReplayPlayStatusChanged@Avatar@GES@@` |

这些名称来自当前 EXE，不是借用其他游戏的接口。

特殊推进 `0x013C5C20`：

1. `0x013C5C2A` 检查 `+0x2D`；未活跃就返回。
2. `0x013C5C46` 临时把 rate 改为 1，`0x013C5C56` 调暂停 setter 解除暂停。
3. 反复处理记录并比较 raw 和 `+0x28`。`0x013C5CD0` 增加常量 `0.10000000149011612`，`0x013C5CE0` 写 raw，随后用 0.1 参数推进多个内部子系统。
4. 记录处理返回 1 时，`0x013C5ED6` 置 `+0x2E = 1` 等待。
5. 完成路径 `0x013C5D73` **先**清 `+0x2D`，再调用 `0x013C6FC0` 更新相关状态，`0x013C5D91` 恢复保存的 rate，`0x013C5DA2` 恢复保存的 pause，最后发完成事件。

由此可确定：快进不是以用户选择的倍速自然播放，也不是简单给 raw 赋目标值。其内部可能经过很多非正常渲染节奏的状态。只读程序即使看到连续增大的 raw，也不能把这段用于轨迹同步。

`+0x2D` 清除早于状态恢复完成，所以“刚看到 flag 清零”还不足以立即接受快照。没有找到可证明整个完成尾部原子结束的单独公开序号；应重采样并等到暂停、时间、对象链及相机矩阵同时稳定。

## 3. 向后跳转的排队、重建和初始化

`0x013A90C0` 为向后跳转路径：

```text
013A90F0  cmp dword ptr [edi+108h],FFFFFFFFh
013A90F7  jne return              ; 避免重复排队
           ... 发 RewindStarted ...
013A918B  call 013CB2F0            ; 清理活动回放推进
013A91A8  mov [ebp-38h],036ED4E4h ; 回调对象 vtable
013A91BF  call 008FFC30            ; 提交延后任务
013A91C4  mov [edi+108h],eax       ; 保存任务 token
```

`0x036ED4E4` vtable 的 `+8` 槽为 `0x013D4F50`，回调：

```text
013D4F56  mov dword ptr [eax+108h],FFFFFFFFh
013D4F63  call 013CA980            ; 重建/初始化
013D4F6F  mov byte ptr [eax+2Dh],1
013D4F76  mov byte ptr [eax+2Eh],0
013D4F84  mov [ecx+35h],al         ; al = (+2C == 0)
013D4F91  mov [ecx+36h],al
```

这证明只检查 `+0x2D` 会漏过已排队、尚未进入特殊推进的窗口。任务 token 在重建开始前已清除，故也不能只检查 `+0x108`。

清理 `0x013CB2F0` 在 `0x013CB320` 清 `+0x11`，取消 tick 注册，清 `+0xA8` 解码器与 `+0xA0` 回放数据；末尾可将 rate 恢复为 1。初始化 `0x013CA980` 则包含：

```text
013CABA1  raw +18 = 0
013CABA8  +2D = 0
013CABC7  +35 = 0
013CAC32  +11 = 1
```

`0x013CAC76–0x013CACD8` 在回放记录元数据中找类型 `0x11`，取该记录的时间写 `+0x64`。这是 origin 的本构建来源证据，并非固定常量 9.8032。

准备回调 `0x013BC550` 将 raw 设为 origin，通知相关子系统，末尾 `0x013BC59C` 置 `+0x36 = 1`、`0x013BC5A0` 清 `+0x2E`。记录处理 `0x013C50A0` 遇类型 `0x11` 时，如果 `+0x36` 尚未就绪便返回等待；否则 `0x013C5136` 置 `+0x35 = 1`，`0x013C513A` 置 `+0x37 = 1`。

因此，raw 为 0、origin 已写、对象指针仍相同，均不意味着重建结束。`+0x11`、`+0x35`、`+0x2D`、`+0x2E` 和排队 token 必须组合检查。具体 UI 的“重新开始”按钮是否复用这一入口，尚未独立追到调用链；重新打开同一回放也必须按新时间会话处理，不依赖 heap 地址变化来识别。

## 5. 第一版保存与未来同步的保守门禁

建议将“有诊断读数”与“允许保存有效机位”分开。失败时可显示原始诊断字段，但禁止把它存成可重复拍摄的有效关键帧。

单次保存前至少要求：

1. EXE 哈希/版本匹配，并由当前对象链证明处于本地回放；确认当前实际渲染相机与原生 Spectator 控制器关系。时钟字段不能代替回放模式门禁。
2. `+0x11 == 1`、`+0x35 == 1`、`+0xA0` 有效；暂停保存额外要求 `+0x12 == 1`。
3. `+0x2D == 0`、`+0x2E == 0`、`+0x108 == 0xFFFFFFFF`。
4. pause/活动/初始化/跳转等 bool 字段只能为 0 或 1；raw、origin、rate 均有限且落在已支持范围。上限如 rate ≤ 64 只是读取器的防坏数据策略，不是客户端官方支持的速度范围。
5. 在读取相机/控制器前后各读取一次时钟和会话身份；暂停时两次 raw、origin、pause、rate、状态门和关键对象链须一致，矩阵/机位内部也必须自洽。再跨采样确认稳定，才发布可保存快照。

稳定窗口可作为首版工程策略，例如连续数次采样覆盖至少两个刷新周期；具体次数/时长不是从 EXE 得出的常数，不能宣称由此获得线程原子性。外部 `ReadProcessMemory` 的“单次读取”本身也不等于冻结游戏状态。极短的跳转可能在两次采样间完成；若没有帧内接入或客户端事件序号，不能绝对排除这种 ABA 漏检。

`+0x36` 可以先记录并要求与已验证样本一致，待动态场景补齐后决定是否硬性要求 1。`+0x37` 的清除依赖正常 tick；仅因它为 1 就断言“正在加载”证据不足。本轮不建议把它当唯一门禁。

| 场景 | 首版暂停保存 | 未来按回放时间同步 |
|---|---|---|
| 已稳定的暂停 | 可以，在机位/矩阵/控制器同时稳定后 | 时间不推进，路径应停在同一参数；独立拍摄时钟可继续 |
| 普通播放 | 本轮未验证，保守禁用保存 | 后续验证后直接用采样的 relative 求路径，不用墙钟累计倍速代替 |
| 用户变速 | 状态变化期间丢弃采样，暂停稳定后可保存 | 保留同一回放时间轴；重置墙钟预测/误差基线，不必将倍速变化视为新回放 |
| 跳转排队、快进、等待或重建 | 禁止 | 当前同步段立即失效；不得沿旧时间差平滑追赶 |
| 完成标志刚清零 | 继续等待稳定条件 | 重新核验时间/对象链后按明确策略重新定位 |
| raw 倒退、origin 改变、对象链改变、重新打开/重播 | 原快照仍可留作离线数据，但拒绝宣称当前会话已匹配 | 建立新会话代次，重新取得锚点；不能只靠相同指针/相同地图 |
| 停止、结束、离开回放，`+11` 清零或数据释放 | 禁止 | 立即失效并释放未来接管权 |
| 非有限值、矛盾状态、读失败、版本不匹配 | 禁止 | 立即失效 |

判断时间跳变时，不能把慢一帧/掉帧误当成跳转，也不能单凭单调递增就认定正常播放。未来需同时记录 monotonic 时间戳、raw/origin/relative、pause/rate、上述状态门、会话代次。先验证正常播放的时钟关系，再设合理的变化阈值；发生不明确的异常，应停止本段同步并重新确认。

## 后续最小只读验证

需要用户手动打开本地回放并操作。程序只观察，不调用上述函数，也不写字段。

1. 先暂停，连续采样，验证当前已有 35.15228 类样本之外的 `+0x11/+0x108` 等门禁，确认不会误拒绝稳定暂停。
2. 用户播放数秒后暂停，再选另一倍速重复；记录 relative 对 monotonic 的斜率、pause/rate 改变次序和相机读取一致性。
3. 用户做一次前跳和一次后跳；逐样本核对 `+0x2D/+0x2E/+0x108/+0x11/+0x35` 变化。采样没捕捉到短暂标志应报告“未观察到”，不能当作该标志无效。
4. 用户重新开始或重新打开同一回放；确认旧同步段必定失效，重建完成后才允许新快照。另测播放结束、离开回放是否及时撤销有效状态。

这轮实验只验证读取边界，不能替代 A 步骤中的机位恢复实验，更不能证明将来的轨迹控制已与渲染帧同步。
